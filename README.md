# 파마파미 컬러 시뮬레이터

침구 색 조합을 웹에서 미리 보고, **맞춤 주문 문의를 한 번에 보낼 수 있게** 만든 페이지입니다.

**→ https://famafami83-del.github.io/famafami-color-simulator/**

기성 상품에 없는 조합은 전부 맞춤 제작입니다. 이 페이지는 **그 맞춤 주문을 받는 창구**입니다.

---

## 쓰는 흐름

| 단계 | 하는 일 |
|---|---|
| **① 디자인** | **사진 카드를 눌러 들어갑니다.** 쇼핑몰 상품 목록처럼 [대표, 2026-08-06] |
| **② 색** | 부위별 색을 원단 **100색**에서 선택. **처음엔 모두 흰색**입니다 |
| **③ 사이즈** | 이불 · 매트리스커버 · 베개커버 각각 **종류 · 사이즈 · 수량** (필요 없는 항목은 「안 할래요」) |
| **④ 확인** | **예상 금액**을 보고, 고른 내용을 **복사해서 문의에 붙여넣기** |

**디자인**

| 디자인 | 사진 | 고르는 부위 | 값 |
|---|---|---|---|
| **무지** | 침대를 옆에서 본 컷 | 6곳 — 이불 / 매트리스커버 / **베개 4곳을 따로** | |
| **양면** | 위에서 비스듬히 본 세로 컷 | 3곳 — **앞면 · 뒷면** / 매트리스커버 | **무지와 같습니다** [대표, 2026-08-06] |

**두 디자인은 사진이 다릅니다** (2026-08-06). 양면을 「삥 구도」로 옮긴 이유는 하나입니다 —
**베개 앞뒤가 한 장에 같이 보입니다.** 뒤 베개는 겉이 앞면색, 앞 베개는 겉이 뒷면색이라
젖혀 놓은 모양입니다. 무지 컷은 베개 네 개가 다 윗면만 보여서 양면 베개를 흉내낼 수 없었습니다.

**맞바꾼 것 — 양면에서는 이불과 베개를 따로 못 고릅니다.** 색 사진 세 장이 전부 베개를
이불과 같은 색으로 칠해놔서 「색이 변하는 자리」로는 둘을 가를 수 없습니다.
대표가 원한 것이 **「이불 바탕을 바꾸면 베개도 같이 바뀌는 것」** 이라 그대로 두었습니다
[대표, 2026-08-06]. 그래서 부위 이름도 `이불·베개 앞면` 처럼 적어둡니다.

**사진에는 삥(테두리)이 있지만 안 보입니다.** 삥은 따로 잡힌 부위인데(`PARTS` 의 `bothP`)
**앞면 색을 따라가게**(`follow`) 두어 봉제선처럼 읽힙니다. 이 제품에는 삥이 없기 때문입니다.
삥 제품을 팔게 되면 `follow` 를 지우고 `DESIGNS` 에 카드 한 장만 더하면 됩니다 —
**사진도 마스크도 이미 들어 있어 용량이 늘지 않습니다.**

**카드를 누르면 바로 색 화면으로 들어갑니다.** 고른 뒤 「다음」을 또 누르게 하지 않습니다.
색 화면 맨 위에 지금 디자인이 적혀 있고, 「디자인 바꾸기」로 한 번에 돌아옵니다.

**폰의 뒤로가기가 한 단계씩 돌아옵니다** [대표, 2026-08-06]. 단계를 브라우저 기록에 남깁니다
(`navigate()`). 안 남기면 뒤로가기가 **페이지를 통째로 벗어나 고르던 것이 전부 날아갑니다** —
양면을 보다가 무지로 돌아가려고 뒤로가기를 누르는 것이 자연스러운데 딴 데로 가버렸습니다.
`goto()` 는 화면만 바꾸고 기록은 건드리지 않습니다. 뒤로가기로 돌아온 것까지 기록에 더하면
뒤로가기가 영영 안 끝납니다. ① 디자인에서 한 번 더 누르면 그때 페이지를 나갑니다.

> `file://` 로 열면 브라우저가 `pushState` 를 막아 이 기능만 조용히 빠집니다 (나머지는 그대로).
> 뒤로가기를 확인하시려면 `npx serve` 같은 걸로 띄워서 보십시오.

**카드 두 장은 사진은 달라도 색은 같게 칠합니다** — 이불은 아몬드 밀크, 매트리스커버는 베링씨.
카드마다 색을 다르게 칠하면 「어느 쪽이 예쁜가」를 고르게 되어 디자인 차이가 묻힙니다.

**디자인을 바꿔도 고른 색은 그대로 둡니다.** 색을 다시 고르게 하면 카드를 둔 뜻이 없습니다.
**아직 손 안 댄 부위에만** 쓰던 색을 물려줍니다 (`CARRY`).

- 물려주지 않으면 — 양면에서 색을 고르고 무지로 가면 흰색부터 다시 골라야 합니다.
- 늘 물려주면 — 무지를 들렀다 오는 사이에 양면에서 고른 **뒷면 색이 앞면 색으로 덮입니다.**
- **베개 색은 못 물려줍니다.** 무지는 베개가 네 부위고 양면은 이불과 한 몸이라 짝이 없습니다.

**종류를 먼저 고릅니다** [대표, 2026-08-05]

| | |
|---|---|
| **이불** | 차렵이불 (솜 일체형) / 이불커버 (커버만) |
| **매트리스커버** | 올인원(누빔) 매트리스커버 / 홑겹 매트리스커버 |

**가격표도 사이즈 목록도 종류마다 따로입니다.**

- **이불커버는 슈퍼싱글이 160×210** 으로 차렵이불(150×210)과 다릅니다. 같은 「슈퍼싱글」이라도
  치수가 달라 한 목록으로 묶으면 틀린 치수가 주문에 나갑니다.
  종류를 바꾸면 사이즈 칸이 다시 채워지고, 고르던 치수가 새 종류에 없으면 퀸으로 돌아갑니다.
- **이불커버를 고르면 두께(온스) 칸이 사라지고, 대신 「이불 연결 똑딱이 갯수」 칸이 나옵니다.**
  솜이 없어 온스가 없기 때문입니다. 감추지 않으면 고르지도 않은 값이 주문에 딸려 나갑니다.
  똑딱이는 갯수만 받고 **값에는 영향이 없습니다.** 안 적으시면 예상 금액 화면에서 적어달라고 알립니다.

**베개커버는 칸마다 사이즈와 장수를 각각 받습니다.** 칸마다 사이즈 + 0~4장을 고르고,
0장인 칸은 주문에서 빠집니다. 40×60과 50×70을 섞어 쓰는 집이 있어서입니다.
수량을 따로 받으면 「4색을 골랐는데 2장」처럼 어느 색인지 알 수 없어집니다.

**이불이 양면이어도 베개커버까지 양면인 것은 아닙니다. 따로 받습니다** [대표, 2026-08-06].
② 색 화면에 **「베개커버도 앞뒤를 다르게」** 칸이 있고, **양면 디자인에서만** 나옵니다 (`DESIGNS.pilTwo`).

| 디자인 | 칸 | 체크 | 베개 칸 | 한 칸의 색 | 주문서 |
|---|---|---|---|---|---|
| **무지** | 칸 없음 | | **4칸** — 사진의 베개 네 개 | **네 칸을 각각** 고른다 | `종류 : 무지 (앞뒤 같은 색)` |
| **양면** | 있음 | **켬**(기본) | **1칸** | 이불 **앞면 · 뒷면** 두 색 | `종류 : 양면 (앞뒤 다른 색)` |
| **양면** | 있음 | 끔 | **1칸** | 이불 **앞면** 한 색 | `종류 : 무지 (앞뒤 같은 색)` |

**「무지」도 주문서에 적습니다.** 안 적으면 대표가 양면인지 아닌지 물어봐야 합니다.
**양면으로 하면 2장까지 10,000원이 더 붙습니다** — 체크칸에 미리 적어둡니다 (「가격」 참조).

**양면은 칸이 하나입니다** [대표, 2026-08-06]. 베개 색이 이불과 한 몸이라 칸을 둘로 나눠봐야
**두 칸의 색이 늘 똑같습니다.** 고를 것이 없는 칸을 둘씩 보여줄 이유가 없습니다.
그래도 칸 자체는 있어야 합니다 — **사이즈와 장수를 받는 자리**이기 때문입니다.
한 칸이 네 칸 몫을 하므로 **장수는 8장까지** 고를 수 있습니다 (`PIL_MODES` 의 `many`).
사이즈를 섞어 쓰실 때는 **「남기실 말」** 로 받습니다.

칸이 하나일 때는 말투와 주문서가 달라집니다 — 「칸마다」가 성립하지 않고, 칸 이름
「베개커버」가 바로 위 제목과 겹치므로 **이름 대신 `사이즈 : 50×70 · 2장`** 으로 적습니다.
체크를 푸시면 사진에는 여전히 베개 앞뒤가 다르게 보이므로,
**③ 사이즈 화면에서 「앞면 색 한 가지로 나갑니다」라고 알려줍니다.**

> 칸 이름(`key`)이 무지와 다릅니다 (무지 `L`·`R`·`L2`·`R2` / 양면 `B`).
> 그래야 무지의 네 칸과 양면의 한 칸이 서로 적어둔 값을 덮지 않고 각각 살아남습니다.
> 보이는 칸이 바뀌므로 맨 위 줄도 `:first-child` 로는 못 잡습니다 —
> `renderPillows()` 가 보이는 첫 칸에 `.first` 를 붙입니다.

**양면인데 앞뒤 색이 같으면 예상 금액 화면에서 알립니다.** 값은 같지만 뒷면을 안 고르신 것일 수
있고, 그대로 두면 대표가 「양면인데 왜 한 색?」을 물어봐야 합니다.

사이즈·장수 칸은 **한 벌만 만들어두고 감췄다 보였다** 합니다. 지우면 양면/무지를 오갈 때
적어둔 사이즈와 장수가 날아갑니다.

## 원단 100색

`FAMAFAMI All Color Chart` 13개 그룹을 그대로 옮긴 **102색**에서, 팔지 않는 **2색을 뺀 100색**입니다.
각 색은 **번호 · 영문명 · 한글명 · 번수(60/80/100수)** 를 갖고 있어 그대로 주문에 씁니다.

**뺀 색** — `953`·`903` 클라우드 화이트 60·80수. 두 색의 값이 `#f5f5f5` 로 완전히 같아
화면에서 구별되지 않는데다 실제로 쓰지 않는 화이트입니다. [대표, 2026-08-05]
빼는 자리는 `build.js` 의 `EXCLUDE` 이고 **번호로 적습니다.**
`swatches.json` 은 컬러차트를 그대로 옮긴 원본이라 손대지 않습니다 —
지우면 차트를 다시 뽑을 때 어긋납니다.

| 그룹 | 색 | 그룹 | 색 |
|---|---|---|---|
| 화이트 · 크림 | 3 | 에이스드 터치 | 4 |
| 라이트 그레이 | 9 | 그린 웨이브 | 13 |
| 딥 그레이 | 15 | 블루 | 9 |
| 어시 레인지 | 17 | 라벤더 | 3 |
| 레드 | 3 | 핑크 | 10 |
| 로즈 와인 | 4 | 번트 오렌지 | 3 |
| 옐로우 | 7 | | |

**매트리스커버는 60수 · 80수만** 고를 수 있습니다 (100수는 얇아서 쓰지 않습니다).
이불 · 베개커버는 100색 전부 가능하고, **매트리스커버는 68색**입니다.

시작 색은 여섯 곳 모두 **NO. 952 멜트 아이스크림 60수**입니다 (`build.js` 의 `WHITE`).
**시작 색은 반드시 60수나 80수여야 합니다** — 100수 색을 넣으면 매트리스커버를 누르는 순간
시작 색이 목록에서 사라집니다. 팔레트에 없는 색이거나 번수가 안 맞으면 **빌드가 멈춥니다.**

| **이불커버** (완제품 크기) | 슈퍼싱글 **160**×210 / 퀸 200×230 / 킹 220×240 / 라지킹 240×240 |
| **매트리스커버** (침대 규격) | 100×200 · 110×200 · 120×200 · 150×200 · 160×200 · 170×200 · 180×200 · 190×200 · 200×200 · 220×200 |

**이불은 종류마다 사이즈 목록이 다릅니다** (슈퍼싱글 150×210 / 160×210). 매트리스커버는
올인원·홑겹이 같은 목록을 씁니다. 종류를 늘리려면 `build.js` 의 `QUILT_KIND` · `MAT_KIND` 에
`sizes` 를 가진 칸을 더하고 **가격표에도 같은 이름의 칸을 만들어야 합니다** — 안 만들면 빌드가 멈춥니다.

## 가격

**맞춤 추가금** — 이불 · 매트리스커버 **+10,000원** (1장당). 사이즈·종류와 무관하며,
이 페이지 주문은 전부 맞춤이라 **항상 붙습니다.**
**베개커버에는 맞춤 추가금이 없습니다** [대표, 2026-08-06].

> 2026-08-04에 베개커버를 「26,000 + 맞춤 3,000」으로 받아 적었는데 **잘못이었습니다.**
> 한 장 **28,000원**이고 맞춤 추가금은 원래 없습니다. 대표가 「두 장이면 56,000원 아닌가」를
> 짚어주면서 드러났습니다 (2026-08-06). 베개커버만 사시면 **「맞춤 추가금이 포함된 금액」
> 문구도 안 나옵니다** — 안 붙는데 붙는다고 말하면 거짓말이 됩니다.

## 고치는 법

```bash
npm i sharp          # 처음 한 번만
node src/build.js    # index.html 다시 만들기
git add -A && git commit -m "..." && git push
```

push하면 몇 분 안에 위 주소에 반영됩니다.

### 폴더 구조

```
index.html      배포되는 페이지. 직접 고치지 말고 build.js로 다시 만든다
colors.json     팔레트 100색 (공개용). build.js 가 만든다
src/
  build.js      index.html 을 만든다 ← 대부분 여기만 고치면 된다
  swatches.json 컬러 원본 데이터
  assets/       디자인마다 흰색 바탕 사진 한 장 + 마스크 한 벌
                base.jpg      + mask_{quilt,mattress,pillowF,pillowR,pillowL,pillowW}.png  ← 무지
                base_both.jpg + mask_{bothA,bothB,bothM,bothP}.png                         ← 양면
                card_plain.jpg / card_both.jpg   ← 디자인 고르는 카드
  tools/        원본 소재가 바뀌었을 때만 쓰는 재생성 도구 (tools/README.md 참조)
```

**`index.html` 을 직접 고치지 마십시오.** `build.js` 를 다시 돌리면 덮어써집니다.
사이즈 목록·부위 이름·안내 문구는 전부 `src/build.js` 위쪽 상수에 모여 있습니다.

### 가격 고치는 법

`src/build.js` 위쪽 `PRICE` 의 숫자만 고치고 다시 빌드하면 됩니다. **여기 말고 가격이 적힌 곳은 없습니다.**

```
PRICE.quilt.sale.charyeop   차렵이불 사이즈별 판매가 4칸
PRICE.quilt.sale.cover      이불커버 사이즈별 판매가 4칸
PRICE.quilt.custom          이불 맞춤 추가금 (1장당). 종류 무관
PRICE.mattress.sale.allinone  올인원(누빔) 침대 규격별 판매가 10칸
PRICE.mattress.sale.plain     홑겹 침대 규격별 판매가 10칸
PRICE.mattress.custom       매트리스커버 맞춤 추가금 (1장당). 종류 무관
PRICE.mattress.height  높이 추가금 구간표 — [{ upto: 35, add: 0 }, …]
                       낮은 높이부터 적는다. upto 이하인 첫 칸이 걸린다.
                       마지막 칸의 upto 가 곧 받을 수 있는 최대 높이다.
                       그보다 높으면 「주문 불가」가 된다.
PRICE.pillow.sale      베개커버 40×60 · 50×70 판매가 (1장당)
PRICE.pillow.custom    베개커버 맞춤 추가금 (1장당). 지금 0 — null 로 두면 「가격 문의」로 샌다
PRICE.pillow.two       양면 베개커버 추가금 — { per: 2, add: 10000 }
                       per 장마다 add 원. 4장이면 20,000원.
                       체크칸 안내 문구도 이 값에서 만들어진다.
```

- **`null` 로 비워두면 그 항목만 「가격 문의」**로 나오고 합계에서 빠집니다.
- **전부 비어 있으면 예상 금액 화면이 아예 안 나옵니다.**
- 높이 구간을 고치면 **화면 안내 문구도 같이 바뀝니다.** 문구를 따로 고칠 필요 없습니다.
- 사이즈 목록을 고쳤는데 가격표를 안 고치면 **빌드가 에러로 멈춥니다.** 조용히 「문의」로 새는 걸 막으려는 것입니다.
- 이불 가격은 **종류와 사이즈로만** 정해집니다. 두께(온스)와 연결 똑딱이 갯수는 가격에 영향이 없습니다.
- 이 페이지 주문은 색을 직접 고른 것이라 전부 맞춤이라, **맞춤 추가금은 항상 붙습니다.**
  기성가로 낼 일이 생기면 `ALWAYS_CUSTOM` 을 `false` 로 바꿉니다.

### 디자인 추가하는 법

디자인 하나는 **바탕 사진 한 장 + 마스크 한 벌 + 카드 한 장**입니다.

1. **사진** — 침구가 전부 흰색인 컷 하나와, 자리마다 **서로 다른 진한 색**으로 칠한 렌더
   **2~3장.** 마스크는 「색이 변하는 자리」를 비교해 뽑으므로 한 장으로는 못 가릅니다.
   한 장 안에서 **따로 고르게 하고 싶은 자리끼리 색이 겹치면 안 됩니다.**
2. **마스크 도구** — `src/tools/split-piping.js` 를 본떠 하나 만듭니다 (`src/tools/README.md`).
3. `src/build.js` 의 **`DESIGNS`** 에 `base`·`card` 를 가진 한 줄, **`PARTS`** 의 각 부위에
   `dz`(나오는 디자인)를 적습니다. 색을 물려주는 규칙은 **`CARRY`** 입니다.
4. 카드 사진은 `src/tools/design-cards.js` 의 **`CARDS`** 에 한 줄 더해 만듭니다.

**마스크·바탕·카드 사진이 없으면 빌드가 멈춥니다.** 디자인마다 이불 부위와 매트리스커버
부위가 하나씩 있는지도 봅니다 — 그 자리만 색이 안 먹거나 주문서가 비는 페이지가
조용히 나가는 걸 막습니다.

### 이미지가 왜 HTML 안에 들어 있나 — 그리고 언제 빼야 하나

CSS 마스크는 `file://` 로 열면 외부 이미지를 못 읽습니다. 분리해두면 **로컬에서 색이 안 먹힙니다.**
그래서 사진과 마스크를 전부 base64로 넣었습니다. base64는 원본을 **33% 부풀립니다.**

| | 사진·마스크 | index.html |
|---|---|---|
| 디자인 1개 (2026-08-05) | 500KB | 942KB |
| 디자인 2개 (2026-08-06) | **660KB** | **1,158KB** |

2026-08-06에 사진이 한 장 더 들어가면서, 무지 바탕 사진을 **품질 92 → 82(mozjpeg)** 로 다시
압축해 394KB를 191KB로 줄였습니다. 화소 평균 차이가 1.9/255라 눈에 안 보입니다 —
색을 곱해 얹는 바탕일 뿐이기 때문입니다.

**디자인이 셋이 되면 이 방식을 버리십시오.** 1.6MB를 넘어갑니다.
사진을 페이지 밖 파일로 빼면 **첫 화면이 250KB로 오히려 가벼워지고**, 누른 디자인 사진만
받아옵니다. 대신 **로컬에서 `index.html` 을 두 번 눌러 여는 확인 방법이 없어집니다** —
`npx serve` 같은 걸로 띄워서 봐야 합니다. 배포된 주소(https)에서는 아무 문제 없습니다.

## 아직 안 된 것

- 예상 금액은 **안내용**입니다. 최종 금액은 문의로 확정합니다.
- **높이 65cm를 넘는 매트리스는 아예 안 받습니다.** 나중에 받게 되면 `PRICE.mattress.height` 에 칸을 더하면 됩니다 — 안내 문구와 최대 높이가 같이 따라갑니다.
- 베개커버는 **무지 한 칸 최대 4장(다 합쳐 16장), 양면 한 칸 8장**까지입니다.
  더 받으셔야 하면 `PIL_QTY` · `PIL_QTY_MANY` 를 늘리면 됩니다.
- 베개커버 사이즈 「**그 외**」는 **뺐습니다** [대표, 2026-08-05]. 값을 못 내는 칸이라 그 줄만
  「가격 문의」로 빠졌는데, 결제를 붙이면 결제가 안 되는 주문이 되기 때문입니다.
  목록에 없는 사이즈는 **「남기실 말」로 받아 따로 안내**합니다.
  자주 들어오는 사이즈가 생기면 `PILLOW` 에 넣고 `PRICE.pillow.sale` 에 값을 주면 됩니다.
- **이제 `PRICE` 에 빈 칸이 없습니다.** 어떤 조합을 골라도 금액이 나오고 「가격 문의」로 새지 않습니다.
  높이 65cm를 넘는 매트리스만 「주문 불가」로 빠집니다 (문의로 넘기지 않는 것이 의도입니다).
- 색상값은 컬러차트 이미지에서 뽑은 값이라 **화면과 실물이 다를 수 있습니다.** 번호와 이름은 차트 그대로입니다.
- **컬러차트에 번호가 잘못 찍힌 칩이 두 장 있었습니다 — 정정 완료.** [대표, 2026-08-05]

  | 색 | 차트에 찍힌 번호 | 맞는 번호 |
  |---|---|---|
  | 다크 그린 100수 | `2027` (애프터 다크의 번호) | **`2029`** |
  | 코코아 그레이 100수 | `2023` (쿨 라벤더의 번호) | **`2031`** |

  고친 뒤 100수가 `2001~2032` 32번 **빈틈없이 정확히** 맞습니다
  (80수 `901~940`, 60수 `951~980`도 빈 번호·중복 없음. 팔레트에서 뺀 953·903 자리만 비어 있습니다).

  바로잡는 자리는 `build.js` 의 **`NO_FIX`** 입니다. `swatches.json` 과 `extract-colors.js` 는
  **차트에 찍힌 그대로** 두어야 대조가 되고, 차트를 다시 뽑아도 정정이 유지됩니다.
  **번호가 겹치면 빌드가 멈춥니다** — 주문서에서 색을 가려낼 수 없게 되는 자리라 조용히 넘기지 않습니다.
  **차트 자체는 아직 틀린 번호로 인쇄돼 있습니다.** 프린톤에 정정을 요청해두는 편이 좋습니다.
- **화면에서 구별되지 않는 색이 있는데, 데이터 문제가 아닙니다.** `#d8baaf` 를 값으로 갖는
  세피아 로즈 80수와 드라이 페탈 100수는 이름이 다른 두 색이지만 **실물 원단이 거의 같은 색**입니다
  [대표, 2026-08-05]. 차트 이미지에서도 ΔE 0.00으로 같게 나옵니다.
  뽑는 과정의 오류가 아니므로 **고칠 것이 없습니다.**
  `#edece7`(머슬린 화이트 80·100수)는 같은 색의 번수 차이라 정상입니다.
  (`#f5f5f5` 클라우드 화이트 60·80수는 2026-08-05에 팔레트에서 뺐습니다.)
- **이름이 다른데 화면에서 구별되지 않는 색쌍이 셋 있습니다.** ΔE 2 미만이라 고객 눈에는 같은 색입니다 —
  `907` 세피아 로즈 80수 ↔ `2008` 드라이 페탈 100수 (0.00),
  `931` 차콜 80수 ↔ `979` 쉐도우 그레이 60수 (1.36),
  `932` 에보니 블랙 80수 ↔ `980` 딥 블랙 60수 (1.54).
  **원단이 실제로 그런 것이라 색상값으로는 풀 수 없습니다.**
  칩 밑에 번수와 번호를 적어둔 것이 지금으로선 유일한 구분 단서입니다 (2026-08-05).
  결제를 붙이면 "화면에선 같아 보였다"가 분쟁이 될 수 있는 자리라, 필요하면
  이 색들만 따로 안내를 붙이는 것을 고려하십시오.
- **색상값 자체는 검증됐습니다.** 차트 102색 전부를 원본에서 전해상도로 다시 뽑아 대조한 결과
  최대 차이가 ΔE 0.9로 육안 구별이 불가능한 수준이었습니다 (2026-08-05).
  차트 칩 수도 13장 전부 세어 102색이 빠짐없이 옮겨졌음을 확인했습니다. **다시 뽑을 이유는 없습니다.**
- **양면은 됩니다. 베개 앞뒤까지 보입니다** (2026-08-06). 아직 없는 디자인은
  **날개형 · 스트라이프 · 삥(테두리)** 입니다. 삥은 **마스크와 사진이 이미 들어 있어**
  카드 한 장만 더하면 되는 상태입니다 (위 「디자인」 참조).

  풀린 경위 — 막고 있던 것은 `양면.jpg`·`양면1.jpg` 구도의 **흰색 바탕**이었습니다.
  대표가 `삥_시뮬레이션_(바탕).jpg` 를 뽑아주면서 **같은 구도의 흰 바탕 + 색 렌더 3장**이
  갖춰졌고, 바탕으로 나누니(`사진 ÷ 바탕`) 그늘이 지워져 부위가 깨끗하게 갈렸습니다.
  전에 「94%가 한 덩어리」였던 것은 흰 바탕이 없어 그늘과 색을 구별하지 못했기 때문입니다.

  **남은 한계** — 이 구도로도 **이불과 베개는 못 가릅니다.** 색 사진 세 장이 전부 베개를
  이불과 같은 색으로 칠해놨기 때문입니다. 따로 고르게 하려면 **베개만 이불과 다른 색으로
  칠한 렌더**가 한 장 더 있어야 합니다.
- **날개형은 사진이 막혀 있습니다** (2026-08-06). 대표께 받은
  `날개형_시뮬레이션용 (바탕).jpg` 는 `날개(검정).jpg` 와 **바이트까지 똑같은 복사본**이라
  쓸 수 있는 사진이 사실상 한 장뿐입니다. 착수하려면 `.tif` 원본(3.2GB)에서 세 장을 내보내야 합니다.

  | 필요한 것 | 왜 |
  |---|---|
  | **날개가 흰색인 바탕** | 색을 곱해서 입히는 방식이라 **검정에 무슨 색을 곱해도 검정**입니다. 지금 사진은 날개가 검정이라 영원히 검정입니다 |
  | **매트리스도 흰색** | 지금 사진의 매트리스는 `rgb(212,219,217)` 로 푸르고 어둡습니다. 곱하면 고른 색보다 탁하게 나옵니다 (이불은 `rgb(251,252,247)` 로 정상) |
  | **색만 다른 렌더 2장 더** | 부위 마스크는 색이 변하는 자리를 비교해 뽑습니다. 한 장으로는 못 가릅니다 |

  구도도 정해야 합니다 — 날개형 사진은 **앞쪽 베개 2개만 뚜렷**한데 무지는 베개 4곳을 따로 고릅니다.
  디자인마다 부위 수가 달라도 되니 2칸으로 줄여도 되고, 뒤쪽까지 보이는 구도로 다시 잡아도 됩니다.
- **날개 색만 적게 고르게 하는 것은 이미 되는 구조입니다.** 매트리스커버가 60·80수만 고르게
  되어 있는 것과 같은 방식(`PARTS` 의 `su`)으로, 정해진 색만 띄우면 됩니다.

## 결제 — 다음에 할 일

**아직 결제 기능은 없습니다.** 어디로 갈지는 정했습니다. 아래는 2026-08-05에 알아본 것이라,
카페24·네이버 정책은 바뀔 수 있으니 착수 전에 다시 확인하십시오.

### 방향 — 카페24 자사몰로 넘긴다

시뮬레이터에 결제를 직접 붙이지 **않습니다.** 대표님께 이미 **카페24 자사몰 + 토스페이먼츠**가
있고, 결제만 붙이는 게 아니라 **주문 조회·배송 등록·부분 취소·환불·정산·세금계산서**가 전부
딸려오기 때문입니다. 그건 카페24가 이미 해주고 있습니다.

스마트스토어가 아니라 자사몰인 이유 — 스마트스토어 수수료에는 **매출연동수수료**가 들어 있는데,
이 주문은 **시뮬레이터가 손님을 데려오므로** 네이버에 통행료를 낼 이유가 없습니다.
(수수료는 자사몰이 2~3%p 낮은 구조입니다. 정확한 값은 계약서를 보십시오.)

### 흐름

```
① 시뮬레이터 확인 화면 → [주문하기]   ← 누르는 순간 주문코드가 자동 복사된다
② 카페24 주문서                      ← 종류·사이즈·수량이 이미 담겨 있다
③ 배송지 입력 + 배송메시지에 붙여넣기 (한 번)
④ 결제
```

**고객이 고른 것을 다시 고르게 하지 않는 것**이 이 설계의 전부입니다 [대표, 2026-08-05].
단계가 늘면 이탈합니다.

### ★ 반드시 알아야 할 제약

카페24 **「바로구매 URL」** 로 주문서에 바로 보낼 수 있는데, 지원 조건이 있습니다.

> 세트 상품과 **독립 선택형 옵션, 파일 첨부 옵션, 추가 입력 옵션**, 진열 안함 상태,
> 상품 분류 미지정 상태, 단독 구매 제한 상품은 바로구매 URL이 지원되지 않습니다.

**「추가 입력 옵션」을 붙이면 바로구매 URL을 못 씁니다.** 그래서 색상 정보를 그 칸으로
받으면 안 됩니다. **배송메시지에 짧은 주문코드(20자 안팎)** 로 받습니다.
옵션은 **조합 일체 선택형** 또는 **조합 분리 선택형**으로 만들어야 합니다.

### 주문코드

주문 내용을 20자 안팎으로 압축한 코드입니다. 대표는 시뮬레이터에 붙여넣어 원문을 복원합니다.
**서버가 필요 없습니다** — 코드 안에 내용이 다 들어 있어 지금 GitHub Pages 그대로 동작합니다.

색은 **팔레트 순번이 아니라 번호로** 저장해야 합니다. 순번으로 저장하면 색이 하나만 늘어도
과거 주문이 전부 어긋납니다. 2026-08-05에 100색 번호를 전부 고유하게 만들어둔 것이 이걸 위한 것입니다.

### 카페24에 등록할 옵션

가격은 **종류 + 사이즈**로만 정해집니다. 색은 가격과 무관하니 **옵션에 넣지 않습니다.**

| 상품 | 옵션 | 조합 수 |
|---|---|---|
| 이불 | 종류(2) × 사이즈(4) | 8 |
| 매트리스커버 | 종류(2) × 규격(10) × 높이(4구간) | 80 |
| 베개커버 | 사이즈(2) | 2 |

손으로 넣으면 실수가 나니 **일괄등록 파일로 만들어 쓰십시오.**

### 착수 전에 확인할 것

1. **바로구매 URL의 실제 형식** — `상품관리 > 상품목록`에서 복사해 봅니다.
   하나의 URL에 옵션을 파라미터로 바꿔 넣을 수 있으면 시뮬레이터가 링크를 그때그때 만듭니다.
   조합마다 URL이 따로 생기면 90개를 표로 넣어둡니다. 어느 쪽이든 됩니다.
2. **비회원 주문을 열어둘 것** — 회원가입 강제가 제일 큰 이탈 요인입니다.
3. **간편결제** — 토스페이먼츠 결제창에 이미 어떤 간편결제가 들어 있는지 먼저 봅니다.
   네이버페이 직접 연동은 **별개 계약이고 수수료도 따로**입니다
   (`판매채널 > 네이버 > 네이버페이 설정`, 평일 약 6시간 뒤 승인, 인증키 4개 입력).
   따로 붙이는 값은 네이버페이 포인트 적립으로 손님을 끌어오는 것입니다.
4. **카카오 회원가입** — SNS 로그인보다 **카카오싱크**가 낫습니다(가입 항목을 받아와 채워줌).
   사업자등록번호를 하이픈 포함해 정확히 넣어야 하고, **대표 운영자 계정**으로 설정해야 합니다.
5. **청약철회 제한 고지** — 맞춤 제작은 제한할 수 있지만 **주문 전에 명시**해야 효력이 있습니다.

### 자체 결제로 가야 한다면

바로구매 URL이 안 되거나 이탈이 심하면 그때 검토합니다. 그 경우 필요한 것:
서버(Vercel Functions 정도면 충분), **금액을 서버에서 다시 계산**(지금 `PRICE` 는 `index.html`
안에 있어 브라우저에서 고칠 수 있습니다 — 견적 안내용으로는 괜찮지만 결제로는 못 씁니다),
그리고 주문 저장·배송·환불·정산을 직접 만드는 일. **결제는 그중 제일 쉬운 부분입니다.**
